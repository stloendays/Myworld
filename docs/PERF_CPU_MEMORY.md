# CPU 与内存减负（2026-10-27）

起因：用户说“想办法优化内存和 CPU 占用，别那么卡”。分支 `feature/perf-cpu-memory`（基于合并了 #31–#33 的 main = dcdc79a），worktree `D:\个人世界\DuskLake-perf`。
测试机：RTX 5060 Laptop（8 GB 显存）、15 GB 内存，高画质，1920×1080 / 1600×900 窗口。

## 1. 先测清楚

| 工具 | 新增的用法 |
|---|---|
| `devtools/Profile.tscn` | `DUSK_PROFILE=全部` 再测投影、地被、声音、卷轴、界面、剧情；`DUSK_PROFILE=隐藏:节点路径,...` 按节点隐藏，看每一类东西占多少绘制调用；开头打印每帧在跑 `_process` 的脚本数量、静态合批结果、各建筑还剩哪些网格没并 |
| `devtools/MemProbe.tscn` | 每次卡顿（> 33 ms）记下那一帧的脚本合计、物理合计、渲染 CPU / GPU、新编译的渲染管线、新读入的声音，以及场景树里哪一棵子树的 `_process` 最慢（树里插计时标记） |
| `devtools/Benchmark.tscn` | `DUSK_BENCH_ONLY=机位1,机位2` 只测这几个机位（笔记本连续跑会发热降频，整轮跑到后半段数字不可信，新旧要短跑、交替比） |

找到的原因：

| 发现 | 数据 |
|---|---|
| CPU 的大头是渲染提交，不是脚本 | 码头机位每帧 6000–7000 次绘制调用，渲染 CPU 8–10 ms；每帧在跑脚本的节点只有约 110 个 |
| 绘制调用从哪来 | 码头机位：泳池馆 1221、树林 878、地被 707、卷轴 606、木屋 507、小动物 378、小溪 318。建筑、码头、卷轴木架都是几百个小方块拼的，每块在主画面和太阳阴影的每一级里各画一次；树林按 64 m 分块，16 种树 + 9 种岩石每块各一组 |
| 地下水族馆在投太阳阴影 | 人在地面上时，太阳阴影的级联照样把缸里的珊瑚、鱼、摆设一件件画进阴影图（馆里没有投影的灯） |
| 远处的东西在投影 | 地被里看得远的灌木、倒木整张图都投影；卷轴在多远都投影，连文字（Label3D）也投影 |
| 进泳池馆、码头时周期性卡 30–60 ms | 图鉴每认出一种新动物，旅行日志就把所有页面（几百个文字标签）整个重建一遍，日志关着也重建（第一次 130 ms） |
| 第一次下雪卡 200–260 ms | 给室外材质挂积雪覆盖层时，Godot 当场为每个材质编译渲染管线（只在第一次） |
| 湖面反射重拍那一帧约 23 ms | 探针 6 个面里要把全图约 36 块地被各画一遍；反射图集每面 1024 像素，2 个槽约 134 MB 显存 |
| 小动物每帧 0.65 ms | 每只每帧算解析地面高度（靠近小溪时要遍历几百个中线点），摆腿时六七个关节的变换推给渲染服务器 |
| 小地图每帧重画 | 底图上几十条抗锯齿折线每帧都画 |
| 进程内存 2.2 GB 里，游戏自己的不到 400 MB | 静态内存 364 MB（其中微软雅黑字体文件 19 MB、各字号的字形缓存 30 MB 左右）；其余是显卡驱动那一侧（无窗口运行整个进程只有 130 MB），和显存、分辨率关系不大 |

## 2. 改了什么

| 改动 | 做法 |
|---|---|
| 静态合批（`scripts/world/StaticBatch.gd`） | 建好湖畔的下一帧（加载画面后面），把建筑、码头、小溪、卷轴木架、山洞、石头小屋里不会动的小网格按材质、24 m 空间格子合成少数几个网格：1324 个并成 715 个。只并没有脚本、没被脚本变量引用、不透明标准材质的部件（门板、灯泡、卷轴杆这类运行时要动、要换材质的都存在脚本变量里，自动跳过）；合成的网格挂在这组成员最近的共同父节点下面，跟着有脚本的那一层一起移动、显隐、删除。玩家、小动物、树林、地被、远景不碰。画面不变 |
| 树林 128 m 一块 | 原来 64 m：每块 25 种模型各一组，树林在主画面和四级阴影里要画上千次。128 m 后绘制调用约少 800 次，三角形多约 25%（GPU 有余量） |
| 投影只留看得见的 | 地被只有离镜头 48 m 内的块投影（每 0.25 秒、走过 6 m 才重新判断）；卷轴离镜头 45 m 外整架不投影；文字从来不投影；泳池馆水族馆那一层（顶板以下）不投影 |
| 地被单独放到渲染层 6 | 湖面反射探针不拍地被；反射图集每面 1024 → 512 像素（倒影由屏幕空间反射为主，看不出差别），显存少 134 MB |
| 日志关着不重建 | 任务、图鉴有变化时左上角追踪栏照常立刻刷新，日志各页只在开着时重建，关着时等下次打开再建 |
| 积雪覆盖层预热 | 加载时先给室外材质挂一次积雪覆盖层再摘掉，渲染管线在加载画面后面编好，真下雪时不再卡 |
| 小动物 | 远处不画（地上的 95 m、天上的 160 m 外，带淡出）；离镜头 30 m 外每 2 帧更新、视野外每 8 帧更新（移动量累积，速度不变）；地面高度走过 5 cm 才重算 |
| 小地图 | 人走动超过 0.2 m 或转身超过 0.6° 才重画，站着不动时每 0.25 秒刷新一次标记 |
| 渲染方式多一个“Direct3D 12（内存占用更少）” | 设置 → 画面 → 渲染方式，下次启动生效（`StartupGuard` 带 `--rendering-driver d3d12` 重启；在 D3D12 下崩了一样会降到兼容渲染）。同样的画面，进程工作集约 1.0 GB（Vulkan 约 2.2 GB）；第一次见到新材质时编译着色器比 Vulkan 慢，Godot 统计的显存也更高，所以默认仍是 Vulkan |

## 3. 结果

**帧率**（1920×1080，高画质，不限帧率；同一台机器上新旧交替各跑两次取平均）：

| 机位 | 改前 FPS | 改后 FPS | 绘制调用 改前 → 改后 |
|---|---|---|---|
| 湖岸出生点 | 91.2 | 133.2 | 2688 → 1714 |
| 码头望木屋 | 65.9 | 119.1 | 6000 → 2561 |
| 木屋室内 | 65.2 | 108.5 | 5353 → 2707 |
| 北部林道 | 80.6 | 114.6 | 4048 → 2114 |
| 秋夜大雨·木屋外 | 94.7 | 136.9 | 2599 → 1470 |
| 泳池馆大厅 | 90.5 | 115.9 | 2066 → 1179 |
| 地下水族馆 | 106.6 | 130.4 | 917 → 679 |
| 石头小屋 | 92.7 | 140.3 | 3930 → 1662 |
| **8 个机位平均** | **85.9** | **124.9（+45%）** | **合计 27601 → 14086（−49%）** |

渲染 CPU 时间平均 6.07 → 4.11 ms（−32%）。先切过下雪、雷雨、仙境夏夜再测的机位也一样变快：冬日下雪 69 → 108、夏夜雷雨 80 → 113、雪山顶 75 → 96、山洞口 134 → 151、图腾石厅 136 → 157 FPS。全图 21 个机位的绘制调用合计 65492 → 34331。

**绕图一圈**（`MemProbe`，1600×900，系统空闲时新旧背靠背各一次）：

| 项 | 改前 | 改后 |
|---|---|---|
| 平均帧时 | 10.23 ms | 8.68 ms |
| 中位帧时 | 9.94 ms | 7.60 ms |
| 最长的一次卡顿 | 260 ms（第一次下雪） | 88 ms（刚进世界） |
| 换到冬天下雪那一下 | 238–260 ms | 34 ms |
| 认出一种新动物 | 30–130 ms | 不到 1 ms |
| 湖面反射重拍那一帧 | 约 23 ms | 约 14 ms |
| 节点数 | 8588 | 7633 |
| 静态内存 | 364 MB | 335 MB |
| Godot 显存计数（其中贴图） | 593 MB（475） | 472 MB（341） |
| 小动物逻辑 | 0.65 ms / 帧 | 0.32 ms / 帧 |

- 剩下超过 33 ms 的帧主要是刚进世界、第一次进木屋时的渲染管线编译（之后有缓存），以及后台程序抢 CPU 时整段变慢（这时脚本、物理、渲染提交同时变慢，绘制调用并不多）。
- 进程工作集在 Vulkan 下还是 2.2 GB 左右，大头在显卡驱动那一侧；想明显少占内存就在设置里选 Direct3D 12（约 1.0 GB）。

**其他试过的**：渲染放到单独线程（`--render-thread separate`）在 CPU 受限的机位能再快约 20%，但 Godot 4.7 下会报贴图更新和退出时的错误，没有开。
